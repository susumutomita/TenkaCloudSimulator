# Engine adapter lifecycle model

This finite model checks one constructor/engine from its initial state. A worker request is one or three against a model budget of two. Production shares eight stack slots and a 32-worker budget with listeners. Singleton checking does not prove the shared multi-engine budget implementation. Constructor validation, slot availability and setup/GOMAXPROCS recheck outcomes are abstract inputs, not validated networking predicates.

## Concrete source correspondence

- `Validate`/`Slot`/`Workers` correspond to `engine.go:89–109`. Invalid configuration consumes nothing; failed worker admission releases the previously reserved slot. The worker count is captured before setup. `Build(FALSE)` aggregates later setup errors and GOMAXPROCS mismatch (`110–141`); cleanup is through the same Close sequence, not an unjoined direct release.
- `DialStart` corresponds to `150–168`: owner mutex excludes Close and atomically checks closed/canceled/single-use state before incrementing the pending-Dial join count. `Cancel` abstracts an independent engine-context cancellation, such as packet-budget termination, without claiming to model its cause. Caller Dial context is abstracted as non-nil/live: its separate preflight Err check, AfterFunc-driven derived-call cancellation, and post-gonet ctx.Err rejection are not modeled. A successful abstract result is therefore not proof of caller-context admission. No second Dial is admitted. There is no claim of live authority at wrapper return: Close may race after registration/dial.Done and the caller may receive an already-closed wrapper. The model intentionally does not require absolute clock < expiry here: this function checks the context error, unlike the explicit absolute-time check in setDeadline.
- `DialResult`, `LateConnectionClosed`, `DialDone` correspond to `169–187`. Successful live connections are registered under owner.mu before dial.Done. A connection obtained after Close/cancellation is closed while holding that mutex, then the pending Dial is joined. Close may already have captured no connection while Dial is still pending, but must wait for the latter path before destroying the stack.
- `MutationStart`/`MutationReturn` correspond to `219–233`. Mutation starts only after dial.Done makes the returned wrapper available. Deadline mutation owns the same mutex, checks both context cancellation and absolute expiry, and clamps zero or overlong requested deadlines to owner expiry. It need not monotonically shorten a previously requested earlier deadline. An already-admitted mutation can finish after absolute expiry; Close cannot acquire the mutex until its setter returns.
- `CloseBegin`, `ResetTimer`, `CloseConnection`, `Destroy`, `ReleaseWorkers`, `ReleaseSlot` correspond to `320–343`. Close seals admission once, cancels the context, detaches link injection, and captures the registered connection while holding the mutex. Independent captured-connection history prevents a repeated Close entry from discarding that cleanup obligation. It requests a raw zero deadline, waits for that call and connection Close to return, joins Dial, closes the link/destroys the stack, then releases worker count and slot in order. A stalled step retains debt because its completion transition cannot occur. No fairness/liveness assertion guarantees it will finish.

`timer` represents the deadline requested through the wrapper, not independently observed gVisor timer state. `timerReset` means the raw reset call has returned. `connClosed` means the Close call has returned, not proof that physical resources were released. Source discards both reset and connection Close errors. This model does not upgrade those ignored errors to success or claim uncertain resources are retained on returned errors; only pending tasks and call ordering are modeled. Stack destruction is likewise an explicit completion signal, not an implementation proof of worker termination.

## Native tests and remaining obligations

Source-backed native witnesses include TestCloseCancelsRealPendingHandshake, TestCapacityAndDeadline, TestConnectionDeadlinesUseAbsoluteOwnerExpiry, TestConnectionDeadlineRejectsElapsedOwnerBeforeCancellation, TestConnectionDeadlineMutationFinishesBeforeCleanup, TestConnectionDeadlineTimersClearedOnClose, TestConnectionCloseInterruptsBlockedIO, TestConnectionDeadlineMutationRacesClose and TestConnectionDeadlineDialCloseRace. Current native tests separately exercise the concrete gVisor behavior assumed at abstract completion points.

Inject/ReadFrame packet parsing, tuple authorization, cumulative packet/byte budgets, copied-buffer ownership, deadlines/cancellation in raw Read/Write, constructor IP/MAC configuration, actual AfterFunc scheduling, stack/link internals and production shared cardinalities remain unmodeled. The packet model may cover its own source, not the entire adapter automatically. No real socket/VM, physical authority, authenticated ownership or operational Battle follows. go.mod/go.sum provenance, checksums, vulnerability scans and dependency behavior remain independent requirements.
